# Implementation Plan: Muni v1 (Typed Lists Second Brain)

**Branch**: `001-typed-lists-companion` | **Date**: 2026-10-15 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/001-typed-lists-companion/spec.md`

## Summary

Muni is an offline-first, installable PWA for four typed lists (shopping, books, movies, recipes). The UI reads and writes only IndexedDB. A sync engine pushes and pulls per-field last-write-wins changes to a TypeScript backend, which stores them in a self-hosted PostgreSQL database with soft deletes, on app open, on reconnect and periodically. The backend is the same Next.js project (route handlers in the Node runtime) and reuses the shared domain code (item model, validation, hybrid logical clock, merge). Users sign in with Google or an email magic link sent over SMTP, with the magic link handled in-house and Google handled by `openid-client` inside one adapter; sessions are server-side in PostgreSQL. Per-user isolation is enforced by server-side authorization: every use case receives the authenticated user id from the session and every repository query is scoped to it. The whole app follows Domain-Driven Design and a hexagonal architecture (ports and adapters): a pure domain model, application use cases that depend only on ports, and adapters (IndexedDB, HTTP, PostgreSQL via Kysely, SMTP, Google OIDC, browser, Next.js UI) at the edges. Deployment target is a self-hosted VPS with Docker Compose (not final).

## Technical Context

**Language/Version**: TypeScript 5.x (strict), Node.js 22 LTS, Next.js 15 (App Router; client components for the UI, route handlers for the backend)

**Primary Dependencies**: Next.js, React 19, Tailwind CSS 4 (hand-built components), `idb` (IndexedDB wrapper), `kysely` with `pg` (node-postgres driver) for data access and migrations, `kysely-codegen` (dev, generates database types), `openid-client` (OIDC for Google sign-in, used only inside its adapter), `nodemailer` (SMTP), `zod` (validation), in-house minimal i18n layer (French message catalog), Serwist (`@serwist/next`) for the service worker and manifest. No Passport and no auth framework.

**Storage**: IndexedDB on device (source of truth for UI); self-hosted PostgreSQL 16 for sync and accounts, accessed with Kysely (typed query builder over `pg`). Schema is managed by Kysely's built-in `Migrator`: migrations are TypeScript files in `db/migrations/`, registered in a static provider (`db/migrations/index.ts`), compiled to JavaScript (`npm run build:migrations`, output `dist/db/`) and run with `node dist/db/migrate.js up` in development, CI and Docker alike. Table types are generated by `kysely-codegen` from the migrated database into the committed file `src/adapters/postgres/db-types.ts`; CI regenerates it and fails if it differs.

**Backend**: Next.js route handlers (`src/app/api/**`, `src/app/auth/**`, Node runtime, no Edge) acting as the driving adapter of server-side use cases, in the same deployable as the UI. They reuse `src/domain` (merge, clock, validation) directly.

**Authentication**: Google sign-in through `openid-client` (OIDC authorization code with PKCE, state and nonce, id-token verification) inside the `OAuthProvider` adapter, and email magic link handled in-house (single-use hashed token with short expiry, sent over SMTP, consumed by the `verifyMagicLink` use case). No passwords, no Passport. OAuth state, nonce and PKCE verifier travel in a short-lived HttpOnly cookie. Sessions are server-side: opaque random token in an HttpOnly, Secure, SameSite=Lax cookie, stored hashed in PostgreSQL with expiry; the first successful sign-in creates the account. `openid-client` is imported only by `src/adapters/google/`; domain and application never see it.

**Architecture**: Domain-Driven Design and hexagonal architecture (ports and adapters) for the WHOLE app, client and server. Dependencies point inward only: `adapters` -> `application` -> `domain`; `domain` imports nothing from the framework, browser, IndexedDB, PostgreSQL, SMTP or Google. Ports are TypeScript interfaces owned by the application layer; adapters implement them. The Next.js UI and the route handlers are driving adapters that call application use cases only. Details in Project Structure below.

**Testing**: Test-driven development (tests first, in every story). Coverage goal 80% (lines, functions, branches, statements) on the logic folders `src/domain`, `src/application`, `src/adapters`, `src/i18n` (UI folders, composition roots and the thin Kysely instance factory and the generated `db-types.ts` excluded), enforced by a Vitest threshold and in CI. Order inside each story: domain tests, port/use-case tests (against in-memory adapters), adapter tests, route handler tests, then UI e2e, each before its implementation. Vitest (unit, use cases, sync engine with `fake-indexeddb`), PostgreSQL integration tests against a test database from Docker Compose, fresh schema per test file built by running the Kysely migrations (including the two-user isolation test), Mailpit for magic-link e2e, Playwright (offline, install, two-context sync scenarios). An architecture test enforces the dependency rule.

**Target Platform**: Mobile-first PWA (iOS Safari 16.4+, Android Chrome), also desktop Chrome/Firefox/Safari. Server: Docker Compose on a self-hosted VPS (app container plus PostgreSQL; TLS reverse proxy not decided).

**Project Type**: Web application (single Next.js project: UI plus backend route handlers, plus Kysely migrations)

**Performance Goals**: Search < 1 s at 5,000 items (SC-006, checked in a unit test); usable < 2 s on repeat visit on mid-range phone, offline included (SC-008, checked manually in the quickstart); sync reaching other devices < 10 s after reconnect (SC-003)

**Constraints**: Offline-first; UI never awaits network; no analytics or third-party tracking; no third-party backend-as-a-service; French only through i18n layer; business logic only in domain and use cases, never in SQL, Kysely repositories, the OIDC adapter or route handlers (the database is storage plus constraints); no dependency on vendor-specific database features beyond PostgreSQL

**Scale/Scope**: One user, up to a few thousand items; about 8 screens (sign-in, home, 4 lists, item detail/edit, search, settings)

## Backend Placement Decision

- **Chosen**: Next.js route handlers in the existing project (Node runtime).
- **Why**: One language, one repository, one Docker image and one deployable; the backend imports `src/domain` directly (merge, clock, zod schemas), so the client and server cannot drift; no inter-service API versioning; fits Simplicity for a single-user-scale app. Hexagonal layering keeps it extractable: route handlers are thin driving adapters over use cases, so the use cases can move into a standalone Node service later without changing domain or application code.
- **Rejected**: A separate Node service (Fastify/Hono): a second deployable and package boundary or monorepo for little benefit at this scale. Next.js server actions: tied to React forms and awkward for the sync client, so plain route handlers are used.

**Mapping of concepts onto the architecture**

| Concept | Now |
|---------|-----|
| Item types, schemas | `src/domain/item.ts` |
| HLC clock and field-level LWW merge | `src/domain/clock.ts`, `src/domain/merge.ts`, used by both client sync and the server `sync-service` |
| Text normalization and matching | `src/domain/text.ts` |
| Local store contract (IndexedDB) | `ItemRepository` port in `application/ports/`, IndexedDB adapter in `src/adapters/indexeddb/`; `application/items.ts` holds the use cases |
| `RemoteStore` | Client port in `application/ports/remote-store.ts`; HTTP adapter in `src/adapters/http/` calls `/api/sync/*`. Server side: `sync-service` use case over the `ServerItemRepository` port, PostgreSQL adapter in `src/adapters/postgres/` |
| Merge and per-user isolation | Merge in the domain, called by `sync-service` (not in SQL); authorization is the use-case contract "userId always from the session, every repository method takes userId", enforced and tested at every layer |
| Auth | `AuthGateway` client port with HTTP adapter; server auth use cases over `UserRepository`, `SessionRepository`, `MagicLinkTokenRepository`, `Mailer`, `OAuthProvider`, `TokenGenerator` ports with Kysely/PostgreSQL, SMTP and Google OIDC adapters |
| UI (`app/`, `components/`) and route handlers | Driving adapters; they call use cases only through the composition roots |

**Dependency rule**: `domain` imports nothing outside itself; `application` imports `domain` and its own ports only; `adapters` import `application/ports` and `domain`; `app`, `components` and `composition` may import `application` and `domain`; only `composition` imports adapters, and only `composition/server.ts` imports server adapters (`postgres`, `mail`, `google`, `node`), so none of them reach the browser bundle. An architecture test fails the build on violations.

**Structure Decision**: Single Next.js project at repository root with a `db/` folder for Kysely migrations and Docker files, organized as domain, application (use cases plus ports) and adapters. Client sync use cases depend only on the `RemoteStore` and `ItemRepository` ports; server use cases depend only on the server ports. This keeps the database, mail and identity providers replaceable (Principle VI) and the UI independent of network and storage (Principle I).

- **M1**: sign-in with the auth backend and PostgreSQL (US1), capture (US2), browse and update (US3). An account-gated, offline-capable app with a working sign-in server.

## Auth Approach (Google OIDC, in-house magic link)

- **Magic link**: in-house use cases (`requestMagicLink`, `verifyMagicLink`) over `MagicLinkTokenRepository`, `Mailer` and `TokenGenerator`; no library.
- **Google**: the `OAuthProvider` port (`begin() -> { redirectUrl, flowState }`, `complete(callbackParams, flowState) -> verified identity | rejection`) implemented by an adapter over `openid-client`, which does discovery, PKCE, state and nonce checks and id-token verification (issuer, audience, expiry, nonce, signature) and requires a verified email. `flowState` (state, nonce, code verifier) is kept in a short-lived HttpOnly cookie by the route handler.
- **Why**: `openid-client` works with plain Web `Request`/`Response` and has no Express or session coupling, so no bridge is needed. Previous Passport and `arctic` options were dropped by the user.
- **Risk**: id-token and PKCE handling is delegated to one library, covered by adapter tests against mocked HTTP and JWKS plus a manual Google check in the quickstart.

## Kysely Types and Migrations (decisions)

- **Types**: `kysely-codegen` generates `src/adapters/postgres/db-types.ts` from the migrated Compose database (`npm run db:codegen`). The generated file is committed (simplest: typecheck, tests and development need no live database; reviewers see schema-type changes in diffs). CI runs migrations, regenerates and fails if `git diff` shows a change (`npm run db:codegen:check`). Alternative: generate only in CI and gitignore the file, which makes local typecheck depend on a database.
- **Migrations**: written in TypeScript with the Kysely schema builder, compiled to JavaScript and run from the app image (no `tsx` or separate migrate image). The static provider means no file-system scanning, and the same registry is used by Vitest (test schema per file), development and production.

## Open Decisions (recommended defaults, awaiting the user)

Settled by the user: in-house magic link; Google through `openid-client` behind the `OAuthProvider` port; Kysely over `pg` with `kysely-codegen` types; Kysely `Migrator` with TypeScript migrations compiled to JavaScript and run from the app image; Docker Compose test database with a fresh schema per test file; sessions in PostgreSQL.

1. Generated types: committed file with a CI freshness check (default). Option: generated in CI only.
2. TLS reverse proxy on the VPS (Caddy, Traefik, nginx) and database backups are not decided and are out of the compose files for now.
3. SMTP provider for production is not chosen (development uses Mailpit).
