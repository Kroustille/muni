# Tasks: Muni v1 (Typed Lists Second Brain)

**Input**: Design documents from `/specs/001-typed-lists-companion/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/ (remote-store.md, auth-api.md, local-store.md, ui-routes.md), quickstart.md

**Architecture**: Domain-Driven Design and hexagonal architecture (ports and adapters) for the whole app, client and server, per plan.md. Layers: `src/domain` (pure model, shared by client and server), `src/application` (use cases and `ports/`), `src/adapters` (IndexedDB, HTTP, browser, PostgreSQL, SMTP, Google OAuth), `src/composition` (client and server wiring), and the Next.js UI and route handlers (`src/app`, `src/components`) as driving adapters. The backend is Next.js route handlers over self-hosted PostgreSQL; no third-party backend-as-a-service. Dependencies point inward only. Work order in every story: domain tests, then port and use-case tests (against in-memory adapters), then adapter tests, then route handler and UI e2e tests, each before the code it covers.

**Tests**: TDD is mandatory. In every phase and story, test tasks come BEFORE the implementation tasks they cover: write the test, see it fail, then implement. Coverage goal is 80% (lines, functions, branches, statements) on the logic folders (`src/domain`, `src/application`, `src/adapters`, `src/i18n`), enforced by a Vitest threshold (T008) and by CI (T111). Pure UI components have no dedicated unit tests; they are covered by e2e scenarios written first. Sync logic, per-user isolation (two-user tests at use-case, PostgreSQL and route level), merge vectors, search normalization, the dependency rule and offline/two-device/install e2e are all kept. The 5,000-item search speed check stays in a unit test (T096); SC-008 (2 s repeat-visit load) is a manual quickstart check (T110).

**Settled choices**: in-house magic link (single-use hashed tokens); Google sign-in through `openid-client` behind the `OAuthProvider` port (no Passport, no auth framework); Kysely over `pg` with types generated by `kysely-codegen` into the committed `src/adapters/postgres/db-types.ts` (CI fails if regenerating changes it); Kysely's built-in `Migrator` with TypeScript migrations compiled to JavaScript and run from the app image; Compose test database with a fresh schema per test file; server-side sessions in PostgreSQL. Still open (see plan.md Open Decisions): the TLS reverse proxy, backups and the production SMTP provider.

**Organization**: Tasks are grouped by user story. Spec priorities: US1 (sign-in), US2 (capture), US3 (browse and update), US4 (sync) are P1; US5 (search) and US6 (home and PWA) are P2. Sign-in is first; sync is a later milestone.

**Milestones**: M1 = Setup, Foundational, US1 (sign-in, including the auth backend and PostgreSQL), US2 (capture), US3 (browse/update). M2 (later) = US4 (sync). M3 (later) = US5, US6, Polish (including Docker deployment).

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependency on incomplete tasks)
- **[Story]**: User story label (US1 to US6); Setup, Foundational and Polish tasks have none
- Paths follow the structure in plan.md (single Next.js project at repo root plus `db/`)

## Dependencies and Execution Order

- **Phase 1 -> Phase 2 -> US1 -> US2 -> US3 (Milestone 1).** Phase 2 blocks everything. Sign-in (US1) comes before capture and browse.
- **Hexagonal order**: domain tests then domain (T010 to T017), ports (T018, T034, T075) then use-case tests and use cases, adapter tests then adapters (T026/T027, T041/T053, T042/T054, T043/T055, T044/T058, T084/T093, T085/T094, T079/T089), route handler tests then route handlers (T045/T057, T080/T090). UI comes last in each story, and only calls use cases through the composition roots. The architecture test (T019) guards the dependency rule from the start.
- **TDD rule (all phases)**: a test task always precedes, and is a dependency of, the implementation task(s) it covers (for example T010 -> T011, T016 -> T017, T022 -> T023/T026, T024 -> T025, T026 -> T027, T036 -> T050, T037 -> T051, T038 -> T052, T039 -> T059, T040 -> T049, T041 -> T047/T053, T043 -> T055, T044 -> T058, T045 -> T057, T063 -> T064 to T068, T069 -> T070 to T074, T077/T078 -> T088, T079 -> T087/T089, T080 -> T090, T082 -> T091, T083 -> T092, T096 -> T098, T100 -> T101 to T103, T104 -> T105, T107 -> T108).
- **US1**: needs Phase 2 (T032, T033) and the Setup Docker/migration tooling (T006, T009). The server track (T034 to T038, T040 to T043, T047 to T056) is independent of the UI and can run in parallel with the client track (T039, T044, T058 to T060).
- **US2**: needs US1 (T062) because the app is gated by sign-in.
- **US3**: needs US2 list view and field editors (T065, T068).
- **US4 (sync, later milestone)**: server track (T075 to T080, T087 to T090) needs US1's server composition, PostgreSQL adapters and session helper (T053, T056, T057); client track (T081 to T085, T091 to T094) needs Phase 2; wiring (T095) needs the session gate (T061) and the sync routes (T090).
- **US5 (M3)**: needs T025; the screen can be built any time after US2.
- **US6 (M3)**: needs Phase 2; home is most useful after US2.
- **Polish and deployment**: after the desired stories are complete. T111 (CI) gates on coverage at 80%, the architecture test, the isolation tests and the tracking check.

```text
Setup (incl. Compose dev + migrations tooling)
  -> Foundational (domain -> ports/use cases -> adapters -> shell)
  -> US1 (sign-in: server auth track || client track) -> US2 -> US3   == Milestone 1
                                                   \-> US4 (sync)    == Milestone 2 (later)
                                                   \-> US5, US6, Polish + Docker deployment == Milestone 3 (later)
```

## Implementation Strategy

- **Milestone 1 (first release target)**: Setup, Foundational, US1 (sign-in and auth backend on PostgreSQL), US2 (capture), US3 (browse/update). Delivers an account-gated, offline-capable typed-list app on one device with a working sign-in server.
- **Milestone 2 (later)**: US4 sync and per-user isolation, completing the P1 scope.
- **Milestone 3 (later)**: US5 and US6 (P2), then Polish and deployment (tracking check, i18n audit, Docker image and Compose, quickstart, CI).
- Tests are written first in every story and must fail before implementation starts; each story ends with a checkpoint and an e2e scenario so it can be validated independently. Coverage must stay at or above 80% on the logic folders, and the hexagonal dependency rule is enforced by the architecture test.
